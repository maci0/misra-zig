# ADR 002: MISRA C:2025

Status: Accepted, 2026-10-27.

## Context

The user asked what MISRA C:2025 holds that applies to Zig. C:2025 has 22 directives and 201 rules. Compared with C:2023 it adds Rules 8.18, 8.19, 11.11, and 19.3, disapplies Rule 15.5, and renumbers Rule 1.2 as Dir 1.2 and Rule 21.2 as Rule 5.10. Every id this standard already cited keeps its number in C:2025.

Each guideline was compared with Zig 0.17.0 using a one-file probe under `.scratch/c2025/`: `rej/` and `comp/` for what compiles, `run/` for what a run does in Debug and ReleaseFast, `more/` for the rest. `docs/misra-c-2025.md` records the result for all 223.

## Decision

The standard cites C:2025 numbers. A guideline is adopted when Zig compiles the hazard and the result is illegal behavior, a crash, or a wrong value:

| Guideline | Hazard in Zig 0.17.0 | misra-lint |
|---|---|---|
| Dir 4.11 | std functions assert their arguments: `log2_int(0)` and `orderedRemove` past the end panicked in Debug and crashed in ReleaseFast | reader |
| Dir 4.15 | `0.0 / 0.0` is NaN and compares false both ways; `@setFloatMode(.optimized)` makes NaN and infinity undefined | `float_mode_optimized` |
| Dir 5.2 | a second `lock` of a held `std.Io.Mutex` hung in Debug and ReleaseFast; two lock orders can deadlock | `lock_twice`; the order is left to a reader |
| Rule 8.14 | `noalias` broken by the caller gave 4 in Debug and 3 in ReleaseSafe and ReleaseFast | `noalias_param` |
| Rule 11.8 | a write through `@constCast` to a constant was lost silently in every mode | `const_cast` |
| Rule 17.1 | `@cVaArg` with the wrong type returned 0 with no check in Debug and ReleaseSafe | `c_variadic` |
| Rule 18.4 | `(p + 6)[0]` past a four-element array read memory with no panic in Debug | `pointer_arith` |
| Rule 19.1 | overlapping `@memcpy` panics in Debug and is unchecked in ReleaseFast | `memcpy_alias` (review) |
| Rule 19.3 | the inactive field of a `union(enum)` panics in Debug; ReleaseFast read the other field's bits | reader |
| Rule 21.25 | an ordering weaker than `.seq_cst` | `atomic_order` |

Dir 5.3 now says each thread is joined once: a second `join` segfaulted in Debug and ReleaseFast.

Choices made for the user:

- `memcpy_alias` is `review`. On a field run it fired on a doubling copy whose two regions cannot overlap.
- `lock_twice` treats an `errdefer` unlock as no unlock, since it does not run on success, and ends a `defer` unlock at the close of its block. A `lock` call with two arguments (`File.lock`) is not counted.
- Rule 15.6 (braces) and Rule 15.7 (final `else`) are left out: `zig fmt` indents a statement after a braceless body at the `if`'s level, and an `if` that yields a value without `else` is rejected.
- Rules 13.2 and 18.9 are not assessed: both compile, and the 0.17.0 language reference states neither an evaluation order nor how long a temporary lives.

## Consequences

- 10 directives and 49 rules in seven groups; 67 checks plus `parse_error`.
- The atomics rule is stricter than common Zig practice. A field run over 1,559 Zig files in other projects found 1,232 weaker orderings; all 8 sampled were atomic operations.
- Other field-run counts: `pointer_arith` 605, `const_cast` 142, `memcpy_alias` 13, `c_variadic` 10, `noalias_param` 2, `lock_twice` 0 after the `errdefer` fix (2 before).
